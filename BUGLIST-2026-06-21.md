## 1. [HIGH] ledSend() blasts colored Note-On to every Grid output on notes 36-51 — EF44 faders (and any non-button element on those notes) light up from DECK A pad colors
- loc: ledSend() ~7137-7150; _ledVel ~7131-7136; LED_OUT.outputs collected by name-match ~7122-7130
- desc: This is the exact bug the user reports. ledSend() walks the ACTIVE deck's current bank and, for every pad whose midiNote != null, sends Note-On [0x90|ch13, midiNote(36..51), colorVel]. It sends this to EVERY MIDI output whose name matches /grid/i — which on an Intech Grid setup is BOTH the BU16 module AND the EF44 module (they enumerate as Grid ports). There is zero awareness of which physical element sits at a given note. The EF44's 4 faders / 4 encoders, if their note range overlaps 36-51 (and per your memory EF44 buttons are note32-39, which overlaps 36,37,38,39), receive the same colored Note-On the app intends for BU16 buttons. The Grid Lua then lights the fader element with DECK A's pad color even though nothing is assigned to that fader in the app. Because the pad has a sample loaded, _ledVel returns 1..8 (palette index+1) and the element lights; an empty pad returns 0 so it clears — which is why it looks like 'DECK A pad colors leaking onto faders.'
- fix: Stop broadcasting to all Grid outputs and stop assuming note==button. Two concrete fixes: (1) Target only the button module: filter LED_OUT.outputs to the BU16 port by exact name (e.g. /BU16|grid.*button/i) instead of /grid/i, OR add a per-output allowlist the user can pick in the LED toggle UI. (2) Restrict the note set you light to the actual pad-button notes of the active grid layout (a constant LED_BUTTON_NOTES = [36..51]) AND ensure those do not overlap the EF44 element notes — since EF44 buttons are 32-39 per the project notes, move the BU16 pad notes to a non-overlapping block (e.g. 48-63) in DEFAULT_NOTES, or give the LED path its own dedicated output+channel that only the BU16 listens on. Minimal immediate patch: change the output filter at ~7127 from /grid/i to a name that only matches the button module, so faders never receive pad Note-Ons.

## 2. [HIGH] handleMIDI ignores the MIDI channel completely — BU16, EF44, and any other controller collide on note/CC numbers
- loc: handleMIDI ~7183-7233 (type = status & 0xF0 discards the channel nibble)
- desc: handleMIDI derives only `type = status & 0xF0` and never inspects `status & 0x0F`. Every Note-On with the same note number triggers the same pad/control regardless of which module or channel it came from. With BU16 on one channel and EF44 on another (or both on ch13), a fader-button press on EF44 that happens to share a note with a BU16 pad will fire that pad. Likewise CC collisions: a master CC learned from one fader will also be driven by any other controller sending that CC number on any channel. This makes routing ambiguous and is a direct cause of 'unexpected things firing.'
- fix: Capture the channel: `const ch = (status & 0x0F) + 1;`. Either (a) gate input handling to the expected controller channel(s) the way LED_OUT.channel already pins ch13 — e.g. ignore notes/CC whose channel isn't in an allowed set — or (b) include channel in the match so pad.midiNote comparisons also check channel. At minimum, store a channel alongside midiNote/midiCC in assignLearn and compare both in handleMIDI so a note on the wrong channel cannot trigger the wrong pad.

## 3. [HIGH] Same notes 36-39 sent to BOTH BU16 and EF44 — EF44 fader LEDs light from DECK pad colors (root cause of reported bug)
- loc: ledSend() ~7144-7148 + ledRefreshOutputs() ~7122-7130; DEFAULT_NOTES ~5328
- desc: ledRefreshOutputs() pushes EVERY output whose name matches /grid/ into LED_OUT.outputs (both 'Intech Grid BU16' and 'Intech Grid EF44'). ledSend() then sends the identical note/velocity stream — notes 36..51 (DEFAULT_NOTES) on ch13 — to all of them. The EF44 module listens on notes 32-39 (per project memory: 4 encoders note32-35, 4 faders note36-39). Pads 1-4 of the active bank use notes 36,37,38,39 — an exact collision with the EF44's four faders. So the four EF44 fader LEDs light up tinted by DECK A's first four pad colors even though nothing is assigned to those faders. This is precisely the user's reported symptom. There is no per-output note mapping or per-module filtering: the app treats every Grid module as if it were the 16-button BU16.
- fix: Introduce per-module routing. Tag each output during ledRefreshOutputs (e.g. detect /bu16/i vs /ef44/i in o.name and store {port, kind}). In ledSend, only send the pad-color notes to BU16-class ports. For EF44 (or any non-BU16 grid port), either send nothing, or send an explicit, separate, intentional LED map for its 4 faders/4 encoders. Concretely: const isPadModule = /bu16/i.test(o.name)||/16/.test(o.name); and skip o.send(msg) for EF44 ports inside the bank.pads.forEach loop. Pair this with an explicit clear of notes 32-47 on the EF44 port so stale fader LEDs go dark.

## 4. [HIGH] Active-deck switch (setActiveDeck) never resends LEDs — stale colors from previous deck remain on the Grid
- loc: setActiveDeck() ~5564-5575 (no render()/ledScheduleSend call)
- desc: setActiveDeck() swaps state.banks to the other deck, ramps deck gain, toggles CSS classes and updates bankInfo, then calls saveStateLocal(). It never calls render() and never calls ledScheduleSend(). Because ledSend() reads state.banks[state.currentBank] (the now-active deck), the Grid LEDs continue to display the PREVIOUS deck's pad colors until some unrelated render() happens. The user switches DECK A -> DECK B and the hardware still shows DECK A's layout/colors — wrong/unexpected LEDs. (saveStateLocal does not render.)
- fix: Add `try { ledScheduleSend(); } catch(_) {}` at the end of setActiveDeck(), or call render() there. Same applies to any code path that mutates state.banks/currentDeckIdx without rendering.

## 5. [HIGH] Single flat note-space + single LED channel = both Grid modules and both decks collide (ROOT CAUSE)
- loc: DEFAULT_NOTES (line 5328), makePad (line 5509), LED_OUT.channel=13 (line 7118), ledSend (lines 7137-7150)
- desc: Every pad in EVERY deck and EVERY bank is born with the same 16 notes 36..51 (DEFAULT_NOTES), and all LED feedback is sent on ONE channel (13) keyed only by pad.midiNote. There is no per-module and no per-deck separation in either the note value OR the MIDI channel. On the Grid hardware the BU16 buttons react to notes 32-47 and the EF44 LEDs react to 32-39 (encoders 32-35, faders 36-39) — all on the same listened channel. Because the app emits notes 36..51 on ch13 for whatever bank/deck is active, those messages physically reach BOTH the BU16 and the EF44 at once: a DECK A pad colored on note 36-39 lights the EF44 encoder/fader LEDs even though nothing is assigned to the fader, and notes 36-47 simultaneously drive BU16 buttons. This is exactly the user's report (EF44 fader LEDs lighting from DECK A pad colors). It also means DECK A and DECK B, sharing 36..51, can never have distinct LED maps. Every other finding below is a symptom of this single design flaw.
- fix: Separate the modules and decks by giving each its own non-overlapping note range AND/OR its own MIDI channel. Concretely: (a) Reserve EF44 (32-39) for control-only and NEVER assign pad notes there — start the BU16 pad map at note 36 only if you also move the EF44 control LEDs off-channel; cleaner is to give pads their own channel distinct from EF44. (b) Make LED_OUT route per module: e.g. ledSend should know which notes belong to BU16 vs EF44 and only emit BU16 pad notes to the BU16 (and never light 32-39 from pad color). (c) Give DECK A and DECK B different channels (e.g. DECK A LED ch13, DECK B LED ch14) or different note banks, then on Grid map each channel/range to the correct physical surface. Add a per-deck `ledChannel` and a `MODULE_NOTE_RANGES` table, and have ledSend()/handleMIDI() filter by them.

## 6. [HIGH] ledSend always blasts notes 36..51 on ch13, lighting EF44 encoder/fader LEDs from pad colors
- loc: ledSend, lines 7137-7150 (status uses LED_OUT.channel=13; loops bank.pads and sends [status, p.midiNote, vel])
- desc: ledSend iterates the active bank's 16 pads and unconditionally sends a Note-On per pad on channel 13. Default notes 36-39 are exactly the EF44 fader LED notes and 40-47 overlap the BU16 upper buttons. So coloring ANY of the first 8 pads (notes 36-43) drives the EF44 LEDs (faders 36-39) plus BU16. There is no concept of which physical surface a note belongs to. Even an empty fader assignment cannot prevent it because the app never knows the EF44 exists.
- fix: Filter the send by a module map. Define e.g. const BU16_NOTES = new Set([36..51 actually used by BU16]); and only send pad LED messages for notes the BU16 actually displays; route EF44 control LEDs (32-39) through a SEPARATE function that is driven by control state, not pad color. Minimal interim fix: shift the BU16 pad note base so pad notes never fall in 32-39 (e.g. pads start at note 48), or send pad LEDs on a dedicated channel the EF44 is NOT mapped to.

## 7. [HIGH] Switching the active deck does NOT refresh the Grid LEDs (stale colors persist)
- loc: setActiveDeck (lines 5564-5575) — calls saveStateLocal() but never render()/ledScheduleSend()
- desc: ledScheduleSend is only called from two places: when MIDI connects (line 7106) and inside render() (line 7790). setActiveDeck updates state.banks to the new deck and saveStateLocal(), but never calls render() or ledScheduleSend(). So after clicking a deck header to make it the routing target, the Grid keeps showing the OLD deck's pad colors until some other action triggers render(). The hardware LED state and the active deck diverge — a direct cause of 'wrong/unexpected LEDs lighting'.
- fix: Add `try { ledScheduleSend(); } catch(_){}` at the end of setActiveDeck (after _applyDeckToState). Better: call a small `ledSyncActiveDeck()` that first ledClearAll() (so the outgoing deck's notes go dark) then ledSend() for the new deck — otherwise notes present in the old deck but absent in the new one stay lit.

## 9. [HIGH] MIDI input matches only the active deck → a note shared by both decks can never reach DECK B
- loc: handleMIDI note path, line 7193 (state.banks[state.currentBank].pads.findIndex(p => p.midiNote === data1))
- desc: Incoming Note-On is matched against the ACTIVE deck's current bank only. Since both decks default to 36..51, the same physical button always plays the active deck and there is no way to address DECK B without first switching the active deck. This is the input-side mirror of the LED collision: one note = two decks, disambiguated only by global active-deck state. A performer pressing a Grid button intending DECK B will trigger DECK A if DECK A is active.
- fix: Once decks have distinct note ranges or channels (finding 3 above), match input against the deck implied by the note/channel: e.g. iterate state.samplerDecks and find the deck whose current bank contains data1 (and/or whose ledChannel matches the incoming status channel), then playPad on THAT deck. This lets both decks be played simultaneously from the Grid without switching the active deck.

## 10. [HIGH] LED feedback broadcasts pad-color Note-On to EVERY Grid output (EF44 lights from BU16 pad colors)
- loc: ledSend / ledClearAll (~7137-7163), ledRefreshOutputs (~7122-7130)
- desc: This is the user's reported bug. ledRefreshOutputs collects EVERY MIDI output whose name matches /grid/i into LED_OUT.outputs. ledSend then loops bank.pads and sends [0x90|ch13, pad.midiNote, colorVel] to ALL of those outputs (LED_OUT.outputs.forEach(o => o.send(msg))). On an Intech Grid rig the BU16 and EF44 are two separate modules that frequently enumerate as separate matching MIDI ports (or one merged 'Grid' port). Pad notes (default 36-51, or 32-47 per the user's BU16 setup) are therefore delivered to the EF44 too. The EF44's Lua maps incoming Note-On on those note numbers onto its fader/encoder LEDs, so DECK A pad colors light EF44 fader LEDs even though nothing is assigned to the fader. There is no per-module / per-element routing: the code has no concept of which output is BU16 vs EF44, and faders/encoders have no midiNote of their own so they should never receive pad-note LED data. ledClearAll has the same flaw (blasts notes 0-127 to all grid outputs).
- fix: Route LED note messages only to the BU16 (button) module, not every /grid/i port. Concretely: (a) in ledRefreshOutputs, separate outputs by name, e.g. push to LED_OUT.padOutputs only ports whose name matches the button module (e.g. /BU16/i, or a user-selectable port) and keep a separate (empty) list for EF44; (b) in ledSend/ledClearAll, send only to LED_OUT.padOutputs. If the hardware exposes a single merged Grid port, instead namespace the pad LEDs onto a note range the EF44 Lua ignores, or gate the EF44 Lua by MIDI channel — but the cleanest app-side fix is per-port targeting so EF44 never receives the pad-note stream.

## 11. [HIGH] MIDI input fires live actions during a KEY learn (and keypresses fire actions during a MIDI learn)
- loc: /Users/nomurahironori/Documents/sampler-studio/index.html handleMIDI lines 7187-7211 and keydown handler lines 7257-7266
- desc: The learn capture is gated on input type asymmetrically. In handleMIDI, learn is only intercepted when state.isLearning.type==='midi' (lines 7188, 7209). If the user started a KEYBOARD learn (clicked 'learn key' on a pad/control) and the connected Intech Grid or MPC sends ANY MIDI note/CC while the learn banner is up, the message is NOT consumed by learn (type is 'key', not 'midi'), so it falls straight through to the live routing at line 7193+ and 7213+: it triggers a pad, or fires FADE OUT / STOP / PAUSE / bank-switch / master-volume. During a live show, the controller constantly emits notes/CC, so opening a key-learn can silently stop playback or jump banks. The symmetric case also exists: while a MIDI learn banner is up, the keydown handler at line 7262 only captures the key when state.isLearning.type==='key', so pressing any keyboard key during a MIDI learn falls through to the pad/control keyboard shortcuts at lines 7318-7350 and fires FADE OUT/STOP/etc. In short, an in-progress learn of one input type leaves the OTHER input type fully live and dangerous.
- fix: While any learn is active, swallow ALL input of both kinds so nothing live fires. In handleMIDI, before the per-type branches add: `if (state.isLearning) { if (state.isLearning.type==='midi') { if (type===0x90 && data2>0) assignLearn({kind:'note',value:data1}); else if (type===0xB0) assignLearn({kind:'cc',value:data1}); } return; }`. In the keydown handler, replace the `if (state.isLearning && state.isLearning.type==='key')` block with: handle Escape->cancelLearn, then `if (state.isLearning) { if (state.isLearning.type==='key') assignLearn({kind:'key',value:e.code}); e.preventDefault(); return; }` so a key press during a MIDI learn is consumed (ignored) rather than triggering a pad/transport action.

## 12. [HIGH] handleMIDI note routing has no appMode gate — MIDI pads, FADE OUT, STOP, PAUSE and bank-switch all fire in DOOR OPEN and MULTI-TRACK modes
- loc: /Users/nomurahironori/Documents/sampler-studio/index.html handleMIDI lines 7187-7206 (note-on branch)
- desc: The note-on branch reads state.banks[state.currentBank] (line 7193) and the control assignments (lines 7200-7205) with no check on state.appMode. Because _applyDeckToState sets state.banks = deck.banks unconditionally (line 5559), state.banks still holds the active sampler deck even while appMode is 'door' or 'multi'. So while the operator is running DOOR OPEN BGM or a MULTI-TRACK setlist, any incoming MIDI note that happens to match a sampler pad note will call playPad and start a sampler one-shot on top of the show, and notes matching bankPrev/bankNext will silently switch the (hidden) sampler bank. The keyboard handler is careful to gate bank-switch behind `if (state.appMode==='sampler')` (lines 7329-7332) and to special-case DOOR/MULTI keys, but handleMIDI was never given the equivalent guard, so MIDI and keyboard behave inconsistently and MIDI leaks sampler triggers into other modes.
- fix: Gate the sampler-only portion of the note-on branch on appMode. Keep the panic transports (STOP/PAUSE/FADE OUT) cross-mode if desired, but wrap the pad lookup and bank switches: `if (state.appMode==='sampler') { const padIdx = state.banks[state.currentBank].pads.findIndex(p => p.midiNote===data1); if (padIdx>=0) { flashPad(...); playPad(...); return; } if (state.controlAssign.bankPrev.midiNote===data1) switchBankRel(-1); if (state.controlAssign.bankNext.midiNote===data1) switchBankRel(+1); }` — mirroring the keyboard handler's `appMode==='sampler'` gating at lines 7329-7332.

## 13. [HIGH] Loading a sample onto an occupied pad keeps the previous pad's trimStart/trimEnd, breaking playback of the new file
